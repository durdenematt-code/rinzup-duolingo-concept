# Map Output and Post-V0.1 Roadmap

## 1. V0.1 map deliverables

Two outputs from `07_map.py`, both reading the same `prospect.gpkg` + a named `score_run`:

### a) QGIS project (`prospecting.qgz`) — the working map

Layer stack (top → bottom):

1. **Field samples** (once they exist) — graduated by colors-per-pan
2. **Gold occurrences** — symbol by `deposit_class` (placer = circle, lode = square) and `dev_status` (size); non-gold occurrences small/grey
3. **Mining claims** — red hatched polygons, active only; closed claims dashed outline, off by default
4. **Stream segments colored by `total_score`** — graduated line color (viridis or similar), line width by stream order; segments with `access_status in (closed, restricted)` get a grey overlay hatch so legal status never hides the geology color
5. **Ownership** — categorized fill at low opacity (USFS green, DNR trust cross-hatch, private beige, state parks purple)
6. **Geology units** — off by default, labeled by unit symbol, `gold_assoc ≥ 2` outlined
7. **Watershed boundaries** (HUC12), study-area boundary
8. Basemap: USGS topo or OpenStreetMap XYZ

QGIS gives click-to-inspect for free: an identify click on a segment shows the `scores` row joined to the flowline. Style files (`.qml`) are generated by the pipeline so restyling survives data reloads.

### b) Self-contained interactive HTML (`map/index.html`)

Folium (fastest) or MapLibre (nicer) export: streams as GeoJSON colored by score, occurrences/claims/ownership as toggleable overlays, popup per segment rendering exactly the spec:

```
Prospectivity: 51/70 (V0.1 — trap score not yet implemented)
  Source:     31/40
  Transport:  14/20
  Confidence:  6/10
Nearest upstream gold source: Calumet mine (lode, past producer)
  Distance downstream: 3.2 km
Upstream gold records: 4
Claim conflict: YES — active placer claim (section-level)
Access: USFS — casual use likely OK; verify current WDFW rules
Below dam: no
```

Popups must carry the caveat line and say "section-level" on claim conflicts — the claim layer cannot tell you which bank of which bend is claimed.

One deliberate simplification: pre-bake the popup HTML per segment at export time. No server, no live queries; the file goes on a phone and works offline.

## 2. How V0.1 evolves (design intent only — do not build yet)

The 30 reserved points in the total score are the contract between V0.1 and Phase 2: later phases fill them without re-architecting.

**Phase 2 — Terrain traps (fills the 30-point trap score).** Ingest WA DNR LiDAR DTM (better than 3DEP 10m where available). WhiteboxTools + Rasterio enter the stack here. Derive per-segment: valley-bottom width / confinement ratio, gradient breaks (longitudinal profile knickpoints), sinuosity and inside-bend inventory, bedrock-exposure proxy (thin-soil + slope + mapped bedrock), terrace/bench detection (REM — relative elevation model above channel). Each trap feature scores per *site* (point along segment), not per segment — Phase 2's map output shifts from "which stream" to "which 50 m of which stream."

**Phase 3 — Gold character indices.** Split the single score into **Coarse Gold Index** (weights: proximity to lode source, high-energy traps, gradient breaks, short transport distance) and **Fine/Flour Gold Index** (weights: long transport, low-gradient depositional bars, flood-deposit surfaces). Same pipeline, two weight profiles — this is why every weight lives in YAML.

**Phase 4 — Reworking/replenishment score.** USGS gauge peak-flow history (Skykomish at Gold Bar gauge) → for each segment, days-since-last-overbank-flow and count of >2-year floods since a site was last worked; segments below Culmback Dam get a permanently degraded replenishment score. Output: "likelihood this bar has been restocked since the last guy cleaned it."

**Phase 5 — Field feedback calibration.** With ≥ ~50 sampled sites (including failures), fit a simple monotonic model (logistic or isotonic regression) from component scores → observed colors-per-pan. This converts the heuristic score into an empirical one and reweights components by what actually predicts your pans. Only after that is any ML (gradient boosting on the full feature stack) worth discussing — with spatial cross-validation, given everything in docs/04 about leakage.

Each phase keeps the same `gpkg` + `score_runs` structure; nothing in V0.1 needs rewriting, only new columns and new weight blocks.
